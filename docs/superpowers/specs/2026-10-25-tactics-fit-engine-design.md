# 战术板 FIT 适配度引擎 · 设计 spec

- 日期:2026-10-25
- 状态:待用户审阅
- 档位:方案 B(适配度引擎);方案 C(对手情报/战争房间)留二期,不在本 spec 范围
- 分期:B1(权重表 + 引擎 + 接口放宽 + 磁贴徽标 + 候选排序)→ B2(一键推荐 + 阵型对比 + 替补角色化)

## 1. 背景与问题

tour 与 club 的数据管道已打通:`player_meta` 表(migrations/0026)每小时从 club 同步**全联盟每名球员**的 71 键属性 + 73 项 PlayStyle 徽章 + 身高;`shared/roleHeat.ts` 已冻结 113 个「位置 × 角色」组合的 5×5 热区;`shared/tactics.ts` 的 PTE26 已有 113 个角色/重心组合。

但战术板排首发时**一个字都没消费这些数据**:首发磁贴与选人下拉只渲染「号码 + 姓名 + 状态角标」;下发接口 `trimPlayerMetaForPool`(worker/lib/playerMeta.ts)主动把 71 键裁成 11 键;属性 pill / 徽章 chip 的渲染组件(src/components/AssignCandidate.tsx)只挂在「队长与定位球」场景,73 枚徽章仅用 3 枚。

**根因:不是缺数据,是情报没有出现在决策现场。** 本 spec 在不动数据管道的前提下,给战术板叠加一层适配度引擎。

## 2. 目标与非目标

### 目标

1. 教练在排首发时能直接看到每名球员对每个槽位角色的适配程度,且分数可解释(非黑箱);
2. 候选选人从「裸姓名下拉」升级为「按适配排序 + 属性/徽章/热区可见 + 可比较」;
3. (B2)一键推荐首发、阵型对比、替补角色化,从推荐改起而非从空白排起。

### 非目标(明确不做)

- 不做对手情报、克制分析、模拟推演(方案 C 二期另立 spec);
- 不改 `tactic_submission` / `tactic` 表结构,不加数据库迁移;
- 不改 12 位战术码格式(码继续只带打法不带球员);
- 不改赛前保密口径(公开端赛前只见历史趋势);
- 不做机器学习/历史表现学习,公式是透明的加权估算;
- 不做拖拽排兵(本期不做,后续可加)。

## 3. 概念与命名(硬规范)

- 全站统一命名:**FIT 适配度**。英文缩写 FIT,中文全称「适配度」。
- **禁止**在 UI 文案里裸称「能力值」「评分」「CAPA」——FC26 游戏内有官方 CAPA(Capabilities)概念,本引擎的分数是 WHL 站点自制估算,**必须在文案上与游戏官方数值区隔**,防止被误读为游戏内数据。**CA/PA 不进 fit 公式、不参与任何排序与档位,但作为参考数据可见**(用户 2026-10-25 修订:原「不展示」定稿过头了):CA 只代表球员在主位置(PosID1)上的整体水平,对其他位置/角色的适配参考有限,所以引擎不读它、排序不吃它;但教练排阵容时应能对照整体水平——候选面板行给 CA 参考列(mono 小字),构成明细给 CA/PA 并标注「不参与 FIT 计算」。fit 的基本盘是「该角色关键属性的加权均值」,人换角色、分就换算。
- **磁贴本体不出现数字**(用户评审定稿):数字是 CAPA 的形态语言,磁贴上改用「角色缩写荧光底衬」(§5.1)从视觉形态上彻底区隔;精确数字只在候选面板行首(列头「FIT 适配度」)、球员卡明细、磁贴悬停提示三处出现。底衬颜色刻意**不用金色**(金色在本系统里是徽章 chip 的专属语义,也进一步与游戏内 CAPA 的常见金色视觉区隔)。

## 4. 架构:四层结构

### 4.1 权重表常量(新 `shared/roleFit.ts`)

- 内容:每个 FC26 **角色**(role 级;精确数量以 PTE26 的 ROLE_FULL 去重为准,探查估约 40 个:Poacher、False 9、Inside Forward……)一份「关键属性 + 权重 + 相关徽章 psid」表。
- **重心(focus)不影响权重**,只影响热区(roleHeat 已有);113 个「位置×角色/重心」组合全部复用角色级权重,维护量小一个数量级。
- **数据驱动初稿已完成并用生产数据验证**(2026-10-23 快照,570 人 × 20 主力角色,脚本 `.tmp/fit-analysis/`):权重取「角色人群 vs 同位置基线」属性差 top6,顺序权重 3/3/2/2/1/1;画像合理(内锋=加速/敏捷/盘带,组织核心=控球/短传/视野)。**偏差实证(用户评审发现)**:「ST 突前前锋」的数据驱动画像算出了弹跳/射门力量——那是站桩中锋(Target Forward)的画像,RoleID 乱给让强力站桩型污染了 AF 人群;且 TF/PO 两个角色未进初稿 top20 目标集。用官方画像手工校对(AF=加速/冲刺/射术/跑位、TF=弹跳/头球/力量、PO=射术/跑位/反应)后:Mbappé 的 AF 68→85(绿,前插型被正确识别),C罗变为 禁区之王 99 + 站桩中锋 94(40 岁终结者画像)——证明「官方定义为准 + 数据驱动校验」的路线正确,也证明**手工定稿本身即可行**(半天量级)。
- **逐角色画像审查结论(用户评审要求全查,2026-10-25)**:全量去档角色 **49 个**(role.json 按位置×角色去重),初稿仅覆盖 familiar 人数 top20。审查结果:
  - **明显偏移(3,除已修正的 AF)**:ST|伪九号(数据画像=纯小快灵,官方 F9 是回撤组织,短传/视野全缺——与 AF 同型的 RoleID 污染);CB|控球后卫(无任何传球属性,官方 BPD 核心是出球——位置共性掩盖);CB|边中卫(画像=普通 CB,官方 WDB 核心是速度覆盖)。
  - **轻偏移(4 组)**:RM/LM/LW|内锋(缺 finishing 内切终结);RM|边锋(缺 crossing);GK|清道夫门将(kicking 权重应升,SK 核心是出击+出球);CDM|镇守(shortpassing 虚高,应为拦截/站位型)。
  - **一致(11)**:CB|后卫、CAM|半边锋、CM|全能中场、CAM|组织核心、CDM|拖后组织核心、CM|组织核心、CM|半边锋、CB|施压、RB|进攻型边翼卫、GK|门将、(已修正的 ST|突前前锋官方版)。
  - **漏算的关键角色(29 个未进初稿)**:CAM|影子前锋(26 人)、ST|禁区之王、ST|站桩中锋、GK|出球型门将、CAM|传统十号位;**位置缺口**——LB 全部 5 个角色、RB 剩余 4 个、RW 除内锋外全部、各位置的边路组织核心(WP)、CDM 中前卫/禁区冲击者等。正式版必须按 49 角色全量出表,否则 LB/RW 等槽位无 fit 可显示。
- **标准来源定调(用户评审)**:权重表与徽章表的**最终标准是 FC26 官方角色定义**(游戏机制层面的关键属性与推荐 PlayStyles),**不是**官方 RoleID 人群——RoleID 在阵容数据里有时乱给,只配当 fit 的小额加分,不配定义画像;上面的数据驱动初稿降级为校验与参考(与官方语义交叉印证)。来源链(按可行性排序):① futbin FC26 角色页(**有人机验证**,抓取先试浏览器头/jina reader,失败即跳过,不阻塞);② FC Editor s901 存档提取;③ **手工定稿(默认主路径)**:按 FC26 官方角色定义逐角色写 6 属性权重(49 角色 × 半天到一天),再用生产数据跑 `.tmp/fit-analysis/` 校验画像合理性——ST 三角色已验证此路可行。任一完成即冻结、测试钉住。
- 徽章相关性初稿已算(同快照,`.tmp/fit-analysis/ps-rel.mjs`):角色人群徽章拥有率 vs 同位置基线,过滤 rate ≥ 25% 且 lift > 0,每角色取 top6;语义与 FC26 官方推荐高度吻合(组织核心=第一脚触球/别出心裁/精准直塞,施压=空中堡垒/封堵,GK=快速反应/远距离抛球),正式版以官方推荐表为准、初稿校验。
- 角色映射已打通:attrs 的 `RoleID1-5` 与 club 仓 `web/assets/ref/role.json` 的 id 空间精确对齐(id 含「位置+角色+熟悉档」,如 142=ST Poacher ++);`PosID1-4` 对应 `ref/position.json`。冻结这两份映射进 shared。
- 冻结后不联网、不依赖 club,升级只在 FC26 版本大改时重新冻结。

### 4.2 评分引擎(新 shared 模块,纯函数;双指标,用户评审多轮定稿)

**FIT 定位(定稿):回答「这个球员自己最适合打哪」——和自己比,不是能力评分。** 不与联盟 CA 水位挂钩(低 CA 球员同样有自己的绿档位置,生产验证:CA 48 的门将个人内 GK 99 分),也不与游戏 CAPA 混同。

两个指标、两个消费场景:

**① 磁贴底衬分(个人内契合,「和自己比」)**
```
score(player, role) = base + badge(银+0.5/金+1,封顶+3)
fitTile(player, role) = score 在该球员全部槽位 score 中的百分位(0-99,最高角色=99)
```
- base = 该角色 6 项关键属性加权均值;fitTile 是**个人内排位**:绿 = 他自己最擅长的前几个位置,橙 = 对他明显浪费的位置;
- PosID/RoleID 不参与个人内比较(已隐含在他的属性结构里;RoleID 有时乱给,不引入);
- **GK 族与场上族分池**:个人内百分位在「GK 族槽位(GK/SK/BPK)」与「场上族槽位」两个池内分别排——否则门将的场上属性普遍极低,池内相对排名会放大噪声(实测:库尔图瓦的 ST 槽位混池排到个人内 89,分池后门将的场上槽位不再出虚高档);
- **位置群兜底(2026-10-25 生产冒烟后补,替代原设想的「绝对弱兜底」)**:分池只挡住跨池比较,池内相对排名仍会让门将「最不差的场上位置」出绿档——生产实测 43 名门将共 257 个场上槽位 fitTile ≥ 85。兜底规则:PosID1-4 任一为 GK → 该球员为门将群,其**场上族槽位一律无档**(灰虚线,title 标「非其位置群」);场上群球员的 GK 族槽位同理无档。「和自己比」只在本人所属位置群内有意义。**不采用绝对分下限**:出球型门将(BPK)的传球属性与低 CA 场上球员重叠、阈值无干净分隔,且任何绝对下限都会连带剥夺低 CA 场上球员的绿档,违背「低 CA 也有最佳位置」定稿;群归属判定用的是位置数据(PosID),不是加分。灰虚线图例语义相应扩为「无数据 / 非其位置群」;
- 生产验证(570 人):官方熟悉角色的个人内分中位 89,与「和自己比」高度一致;C罗绿=突前锋+中前场,中卫绿=CB 三件套,低 CA 门将绿=GK。

**② 候选面板分(槽位绝对分,「和联盟比」,选人排序用)**
```
fitRank(player, role) = min(99, round(base + 2×位置匹配 + 3或5×角色熟悉 + ≤3×徽章))
```
- 统一标尺、跨球员可比,回答「这个位置上谁更强」;加分项维持用户定稿不变(PosID 命中 +2;RoleID 一档 +3 / ++ 档 +5;徽章封顶 +3);
- 排序与行首数字用它;**排序用未截断值,显示层 min(99)**(顶级 14 人会到 100-105,封顶只影响显示不压平排序);
- 各角色联盟最佳人选的原始分 top1 约 96-105、一线主力 p90 约 85-89(生产实测)。

- 两个分数都带 breakdown(构成明细:属性贡献、徽章加成、个人内排位/加分项),不黑箱;
- CA/PA 不进任何公式、不参与排序与档位(§3 修订口径:作参考展示——候选行 CA 列、明细 CA/PA);
- 球员无 meta 时两个分都返回 `null`,UI 显示「无数据」;
- 单测钉住:权重表覆盖全部 PTE26 角色、区间、breakdown 一致性、个人内百分位定义、加分封顶。

## 5. UI 视觉规格(基于现有样式体系,不引入新色)

现有设计语言(实测自 src/styles.css):主色草皮绿 `--pitch #0e7a46`;磁贴深墨绿半透 `rgba(26,36,32,0.78)`、92px 宽、圆角 9、数字全 JetBrains Mono(`--font-mono`);警示红 `#c92a2a`;比赛日橙 `--live #e8590c`;金银徽章 chip `.asg-chip.gold/.silver`;属性 pill `.asg-pill`;热区三层绿 `.tac-heat-1/2/3`。

### 5.1 磁贴标记:角色缩写荧光底衬(磁贴上无数字,用户评审定稿)

磁贴两行结构(位置码 + 角色缩写 / 姓氏)完全不动,唯一变化是**角色缩写下加 3px 荧光底衬**(inset box-shadow 实现,只罩住缩写约 34px 宽):

```
┌──────────────┐
│ ST AF-A      │   ← AF-A 下绿/黄/红橙荧光衬
│ 张           │
└──────────────┘
```

| 档位 | 条件(个人内契合分) | 底衬色 | 语义 |
|---|---|---|---|
| 绿 | fitTile ≥ 85 | #00c882(与热区二层绿同源) | 他自己最擅长的位置(个人内前 ~15%) |
| 黄 | 50 ≤ fitTile < 85 | #d9c34a | 他的中游选择 |
| 红橙 | fitTile < 50 | #e0562e(刻意停在橙域,不进停赛红 #c92a2a 语义区) | 对他明显浪费的位置(个人内后一半) |
| 灰虚线 | 无 meta | rgba(244,246,243,.35) dashed | 缺数据是事实,不是 0 分 |

- 底衬分**只做个人内比较**(与自己比),不跨球员比较——跨球员的强弱对比走候选面板的绝对分(fitRank,统一标尺);悬停提示显示两个数:`个人内契合 94 · 该位置水平 86(本站估算,非 FC26 游戏内 CAPA)`;
- 「划重点」语言:衬标记的是「这个人 × 这个角色」的搭配,不评判人;换人/换角色后衬色跟着变;
- 底衬为文字下衬,不占布局高度——磁贴 92×44、摆位表与 `tests/pitch.test.ts` 零改动;
- 不用红色:红是「停赛/伤停/重复占位」的硬错误语义;不用金色:徽章 chip 专属,亦与游戏内 CAPA 视觉区隔;
- 色觉障碍下绿/黄区分度有限,靠悬停数字与候选面板兜底;
- 阈值 85/50 按个人内百分位语义定稿(前 15% 绿、后 50% 橙);候选面板绝对分无档位色,只有排序与数字。

**窄屏(≤560px)结论(实测现状后定)**:磁贴 92px 定宽不缩放,靠摆位表横向错位防重叠(一档仅 49px);底衬不占横向空间与布局高度,窄屏零挤占。触屏无悬停:点磁贴走底部弹层候选列表,FIT 数字与排序在弹层里看,信息获取路径不依赖悬停。

**精确数字的落点**:候选面板行首(列头「FIT 适配度」= 绝对分,按分排序)、球员卡当前槽位明细(两个分与构成)、磁贴悬停提示。磁贴本体无数字——与 CAPA 的数字形态从根上区隔。

### 5.2 候选面板(复用 asg- 组件系)

点磁贴弹出的选人面板沿用 AssignCandidate 的视觉语言(灰底属性 pill、金银徽章 chip、虚线「无数据」胶囊),教练零学习成本。差异三点:

1. **排序换 FIT 降序**,行首是 mono 大号分数,列头标「FIT 适配度」;分数旁给 **CA 参考列**(mono 小字,标注不参与 FIT);停赛/伤停后缀保留;
2. 每行只显示**该角色相关**属性 pill(权重前三)与徽章 chip,不堆全量;
3. 点行**展开构成明细**:横条贡献图(关键属性:名称 + mono 数值 + 加权贡献条)+ 徽章加成 + 该槽位 5×5 热区缩略(40px 方格,复用 .tac-heat 三层绿色值)——「分数为什么是这个数」一眼看懂,不黑箱。

无 meta 球员排末尾,标「无数据」。

### 5.3 一键推荐(B2)——先预览 diff,确认才应用

- 推荐按钮放提交卡上方,次级按钮样式,不放球场内;
- 点击后**不直接改动阵容**,先出对比列表:每行「王五 出 → 李四 入(ST),FIT 64 → 87,+23」;教练看完点「应用」才生效——diff 预览即知情确认环节;
- 算法:11 槽 × 全队候选的二部图最大权匹配(匈牙利算法,n≤30 纯前端毫秒级),**优化目标用绝对分 fitRank**(排出该阵型下最强的 11 人分配);新 shared 模块,单测钉住(含「两人都最适合 ST」的冲突用例)。

### 5.4 阵型对比(B2)

每个阵型旁标 mono 小字总分(该阵型最优分配后的全队总 FIT),展开看短板槽位排序。选阵型从凭记忆变成看排序。

### 5.5 替补角色化(B2)

替补每人标注「覆盖哪些槽位 + FIT」,按角色补强而非按名字堆人。

## 6. 免责条款(三层落位,不弹窗、不勾选)

核心口径(用户定):**评分与推荐不保证赛场表现**;附带区隔声明(非游戏官方数值)。

| 位置 | 文案 |
|---|---|
| 页脚常驻(lineup 区现有声明行追加) | FIT 适配度与自动推荐为本站估算,不构成对比赛表现或成绩的任何保证 |
| FIT 图例行(热区图例旁同款小字) | FIT 适配度按最近一次同步的 FC26 属性与徽章加权估算,非游戏内 CAPA 或官方数值 |
| 推荐 diff 面板顶部(最完整版) | 推荐由系统按当前同步数据自动计算,不保证实际比赛表现;排兵决定权在教练 |

## 7. 保密边界(硬约束)

FIT 徽标、候选面板、推荐、阵型对比**只渲染在教练端与代打板**。公开端比赛页、赛前情报页零渲染、零接口暴露——评分本身是本队战术思路的泄露面,与「赛前不亮牌」同一口径。公开 lineup DTO(lineup.ts 的 full/captain/none 三档)不携带任何 FIT 字段。

## 8. 分期

- **B1**:权重表 + 评分引擎 + trimPlayerMetaForPool 放宽 + 磁贴徽标 + 候选排序面板 + 免责三层落位。工期量级 1-2 周。
