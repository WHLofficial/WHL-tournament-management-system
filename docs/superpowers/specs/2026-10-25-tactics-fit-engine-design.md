# 战术板 FIT 适配度引擎 · 设计 spec

- 日期:2026-10-25
- 状态:待用户审阅
- 档位:方案 B(适配度引擎);方案 C(对手情报/战争房间)留二期,不在本 spec 范围
- 分期:B1(权重表 + 引擎 + 接口放宽 + 磁贴徽标 + 候选排序)→ B2(一键推荐 + 阵型对比 + 替补角色化)

## 1. 背景与问题

tour 与 club 的数据管道已打通:`player_meta` 表(migrations/0026)每小时从 club 同步**全联盟每名球员**的 71 键属性 + 73 项 PlayStyle 徽章 + 身高;`shared/roleHeat.ts` 已冻结 113 个「位置 × 角色」组合的 5×5 热区;`shared/tactics.ts` 的 PTE26 已有 113 个角色/重心组合。

但战术板排首发时**一个字都没消费这些数据**:首发磁贴与选人下拉只渲染「号码 + 姓名 + 状态角标」;下发接口 `trimPlayerMetaForPool`(worker/lib/playerMeta.ts)主动把 71 键裁成 11 键;属性 pill / 徽章 chip 的渲染组件(src/components/AssignCandidate.tsx)只挂在「队长与定位球」场景,73 枚徽章仅用 3 枚。

**根因:不是缺数据,是情报没有出现在决策现场。** 本 spec 在不动数据管道的前提下,给战术板叠加一层适配度引擎。

## 2. 目标与非目标

### 目标

1. 教练在排首发时能直接看到每名球员对每个槽位角色的适配程度,且分数可解释(非黑箱);
2. 候选选人从「裸姓名下拉」升级为「按适配排序 + 属性/徽章/热区可见 + 可比较」;
3. (B2)一键推荐首发、阵型对比、替补角色化,从推荐改起而非从空白排起。

### 非目标(明确不做)

- 不做对手情报、克制分析、模拟推演(方案 C 二期另立 spec);
- 不改 `tactic_submission` / `tactic` 表结构,不加数据库迁移;
- 不改 12 位战术码格式(码继续只带打法不带球员);
- 不改赛前保密口径(公开端赛前只见历史趋势);
- 不做机器学习/历史表现学习,公式是透明的加权估算;
- 不做拖拽排兵(本期不做,后续可加)。

## 3. 概念与命名(硬规范)

- 全站统一命名:**FIT 适配度**。英文缩写 FIT,中文全称「适配度」。
- **禁止**在 UI 文案里裸称「能力值」「评分」「CAPA」——FC26 游戏内有官方 CAPA(Capabilities)概念,本引擎的分数是 WHL 站点自制估算,**必须在文案上与游戏官方数值区隔**,防止被误读为游戏内数据。
- **磁贴本体不出现数字**(用户评审定稿):数字是 CAPA 的形态语言,磁贴上改用「底部微型适配条」(§5.1)从视觉形态上彻底区隔;精确数字只在候选面板行首(列头「FIT 适配度」)、球员卡明细、磁贴悬停提示三处出现。适配条颜色刻意**不用金色**(金色在本系统里是徽章 chip 的专属语义,也进一步与游戏内 CAPA 的常见金色视觉区隔)。

## 4. 架构:四层结构

### 4.1 权重表常量(新 `shared/roleFit.ts`)

- 内容:每个 FC26 **角色**(role 级;精确数量以 PTE26 的 ROLE_FULL 去重为准,探查估约 40 个:Poacher、False 9、Inside Forward……)一份「关键属性 + 权重 + 相关徽章 psid」表。
- **重心(focus)不影响权重**,只影响热区(roleHeat 已有);113 个「位置×角色/重心」组合全部复用角色级权重,维护量小一个数量级。
- 数据来源备选链(依次尝试,任一成功即冻结):
  1. futbin FC26 角色页抓取(与 roleHeat 同法:抓取 → 生成 TS 常量 → 测试钉住);
  2. FC Editor s901 存档提取(scripts/fc26-id-rekey 时期用过,数据可信);
  3. 手工整理(一次性,约 40 角色 × 每角色 4-6 项关键属性)。
- 冻结后不联网、不依赖 club,升级只在 FC26 版本大改时重新冻结。

### 4.2 评分引擎(新 shared 模块,纯函数)

```
fit(player, role) = min(99, round( Σ(attrᵢ × wᵢ) / Σwᵢ + badgeBonus ))
badgeBonus = 1.5 × 相关金徽数 + 0.5 × 相关银徽数,封顶 +5
```

- 权重 wᵢ 按关键属性顺序取 3, 3, 2, 2, 1, 1(最多 6 项,前两项并列核心)——设计值,实施时可整体校准但必须保持「加权平均天然落在 0-99 区间」的性质。
- 返回值带 breakdown:`{ score, attrs: [{key, value, weight, contribution}], badges: [{psid, tier, bonus}], missing: [缺失的关键属性键] }`,供 UI 展开明细。
- 属性取自 `player_meta.attrs`(club 下发的英文键);球员无 meta 时返回 `null`,UI 显示「无数据」,不显示 0 分。
- 单测钉住:权重表覆盖全部 PTE26 角色、分数区间、breakdown 加和一致性。

### 4.3 接口放宽(worker,一处小改)

- `trimPlayerMetaForPool`(worker/lib/playerMeta.ts)从 11 键放宽到 fit 所需键集(权重表用到的键的并集;预估 ≤ 30 键,不必全量 71 键)。
- 不改表、不加迁移、不动同步链路(clubRoster/clubMeta 原样)。
- 实施时实测 bootstrap payload 增量,写进 PR 描述。

### 4.4 战术板 UI(src/pages/Tactics.tsx 为主)

见 §5 视觉规格。

## 5. UI 视觉规格(基于现有样式体系,不引入新色)

现有设计语言(实测自 src/styles.css):主色草皮绿 `--pitch #0e7a46`;磁贴深墨绿半透 `rgba(26,36,32,0.78)`、92px 宽、圆角 9、数字全 JetBrains Mono(`--font-mono`);警示红 `#c92a2a`;比赛日橙 `--live #e8590c`;金银徽章 chip `.asg-chip.gold/.silver`;属性 pill `.asg-pill`;热区三层绿 `.tac-heat-1/2/3`。

### 5.1 磁贴底部适配条(三档色 + 长度编码,磁贴上无数字)

磁贴两行结构(位置码 + 角色缩写 / 姓氏)完全不动,在磁贴**最底部**加一条 3px 微型条:

```
┌──────────────┐
│ ST AF-A      │
│ 张           │
│ ▁▁▁▁▁▁▁▁▁▁   │   ← 3px 条:填充长度 = fit%,档色绿/灰/橙
└──────────────┘
```

| 档位 | 条件 | 样式 | 语义 |
|---|---|---|---|
| 绿 | fit ≥ 85 | 填充 #00c882(与热区二层绿同源) | 合适 |
| 灰 | 70 ≤ fit < 85 | 填充 rgba(244,246,243,.6) | 能用,不抢眼 |
| 橙 | fit < 70 | 填充 #f08c4d(--live 系亮橙) | 留意,可能错配 |
| 无条 | 无 meta | 不渲染条 | 缺数据是事实,不是 0 分 |

规格细节:

- 条为 absolute 定位贴底(left/right 5px、bottom 3px),**不占布局高度**——磁贴尺寸 92×44 一切照旧,现有摆位表与 `tests/pitch.test.ts` 的错位逻辑零改动;
- 档色编码外冗余**长度编码**(填充 = fit%):色觉障碍下仍可从条长读出相对高低;
- 不用红色:红在本系统是「停赛/伤停/重复占位」的硬错误语义,FIT 是参考不是判决;不用金色:徽章 chip 专属,亦与游戏内 CAPA 视觉区隔;
- 悬停提示(title):`FIT 适配度 87(本站估算,非 FC26 游戏内 CAPA)`;
- 阈值 85/70 为设计值,写进测试钉住。

**窄屏(≤560px)结论(实测现状后定)**:磁贴 92px 定宽不缩放,靠摆位表横向错位防重叠(一档仅 49px);适配条不占横向空间与布局高度,窄屏零挤占。触屏无悬停:点磁贴走底部弹层候选列表,FIT 数字与排序在弹层里看,信息获取路径不依赖悬停。

**精确数字的三个落点**:候选面板行首(列头「FIT 适配度」,按分排序)、球员卡当前槽位明细、磁贴悬停提示。磁贴本体只有条,无数字——与 CAPA 的数字形态从根上区隔(用户评审定稿)。

### 5.2 候选面板(复用 asg- 组件系)

点磁贴弹出的选人面板沿用 AssignCandidate 的视觉语言(灰底属性 pill、金银徽章 chip、虚线「无数据」胶囊),教练零学习成本。差异三点:

1. **排序换 FIT 降序**,行首是 mono 大号分数,列头标「FIT 适配度」;停赛/伤停后缀保留;
2. 每行只显示**该角色相关**属性 pill(权重前三)与徽章 chip,不堆全量;
3. 点行**展开构成明细**:横条贡献图(关键属性:名称 + mono 数值 + 加权贡献条)+ 徽章加成 + 该槽位 5×5 热区缩略(40px 方格,复用 .tac-heat 三层绿色值)——「分数为什么是这个数」一眼看懂,不黑箱。

无 meta 球员排末尾,标「无数据」。

### 5.3 一键推荐(B2)——先预览 diff,确认才应用

- 推荐按钮放提交卡上方,次级按钮样式,不放球场内;
- 点击后**不直接改动阵容**,先出对比列表:每行「王五 出 → 李四 入(ST),FIT 64 → 87,+23」;教练看完点「应用」才生效——diff 预览即知情确认环节;
- 算法:11 槽 × 全队候选的二部图最大权匹配(匈牙利算法,n≤30 纯前端毫秒级),新 shared 模块,单测钉住(含「两人都最适合 ST」的冲突用例)。

### 5.4 阵型对比(B2)

每个阵型旁标 mono 小字总分(该阵型最优分配后的全队总 FIT),展开看短板槽位排序。选阵型从凭记忆变成看排序。

### 5.5 替补角色化(B2)

替补每人标注「覆盖哪些槽位 + FIT」,按角色补强而非按名字堆人。

## 6. 免责条款(三层落位,不弹窗、不勾选)

核心口径(用户定):**评分与推荐不保证赛场表现**;附带区隔声明(非游戏官方数值)。

| 位置 | 文案 |
|---|---|
| 页脚常驻(lineup 区现有声明行追加) | FIT 适配度与自动推荐为本站估算,不构成对比赛表现或成绩的任何保证 |
| FIT 图例行(热区图例旁同款小字) | FIT 适配度按最近一次同步的 FC26 属性与徽章加权估算,非游戏内 CAPA 或官方数值 |
| 推荐 diff 面板顶部(最完整版) | 推荐由系统按当前同步数据自动计算,不保证实际比赛表现;排兵决定权在教练 |

## 7. 保密边界(硬约束)

FIT 徽标、候选面板、推荐、阵型对比**只渲染在教练端与代打板**。公开端比赛页、赛前情报页零渲染、零接口暴露——评分本身是本队战术思路的泄露面,与「赛前不亮牌」同一口径。公开 lineup DTO(lineup.ts 的 full/captain/none 三档)不携带任何 FIT 字段。

## 8. 分期

- **B1**:权重表 + 评分引擎 + trimPlayerMetaForPool 放宽 + 磁贴徽标 + 候选排序面板 + 免责三层落位。工期量级 1-2 周。
- **B2**:一键推荐(匈牙利算法)+ 阵型对比 + 替补角色化。工期量级 1 周。
- B1 独立可用、独立可发布;B2 依赖 B1 的引擎。

## 9. 测试策略

1. 权重表完整性:roleFit 覆盖 PTE26 全部角色,无孤儿角色(测试钉住,新增角色漏配权重表时 CI 红);
2. 引擎单测:分数区间 [0,99]、breakdown 加和 = score、无 meta 返回 null、徽章封顶 +5;
3. 推荐算法单测(B2):最优性抽查、冲突用例、空候选用例;
4. 阈值钉住:85/70 分档边界;
5. UI 冒烟:磁贴适配条四态(绿/灰/橙/无数据不渲染)渲染;候选面板排序与展开;窄屏(≤560px)磁贴尺寸与摆位零回归;
6. payload 实测:放宽后 bootstrap 响应体增量记录进 PR;
7. 回归:现有 tests/(tactics、playstyles、playerMeta、assignRelevance 等)全绿。

## 10. 风险与备选

| 风险 | 缓解 |
|---|---|
| 权重表数据源不可得 | 备选链 futbin → FC Editor s901 → 手工整理;最坏 40 角色 × 4-6 属性,半天工作量 |
| 评分被当成唯一真理 / 误认为游戏 CAPA | 磁贴本体无数字、只有形态独立的底部条(§3/§5.1)+ 免责三层(§6)+ 档色不用金红;推荐走 diff 确认制 |
| payload 膨胀 | 只放宽权重表键并集(≤30 键),实测把关 |
| FC26 版本更新致权重过期 | 冻结制,大版本时重抓;权重表头部注释标冻结日期与来源 |
